## 变量总览

先分两类：**请求自身的状态**（`request.xxx`，跨调度步持续存在）和 **本步调度用的局部变量**（每次 `schedule()` 重新创建）。

| 变量 | 归属 | 含义 | 你的例子 `[t0..t3] → t4` | 谁更新 / 来源 |
|---|---|---|---|---|
| `request.num_prompt_tokens` | 请求状态 | **prompt 长度** $P$，即输入侧 token 数。构造时确定，**整个生命周期不变**（streaming session 除外） | `4` | `Request.__init__` 里由 `prompt_token_ids`/`prompt_embeds` 长度算出 |
| `request.num_tokens_with_spec` | 请求状态（property） | **"这个请求目前已知的全部 token 数（含草稿）"**<br>= `len(_all_token_ids)` + `len(spec_token_ids)`<br>= prompt + 已返回输出 + 投机草稿 | prefill 时 `4`<br>decode 时 `5, 6, ...` | 只读属性：`num_tokens + len(spec_token_ids)` |
| `request.max_tokens` | 请求状态 | **用户要求的最大生成 token 数** $M$（来自 `sampling_params.max_tokens`）。pooling 模型固定为 1 | 假设 `max_tokens=3` | `Request.__init__`，取自采样参数，不变 |
| `request.num_computed_tokens` | 请求状态 | **进度条**：已经被模型 forward 过、KV 已写入 cache 的 token 数。<br>是最关键的记账变量 | `0 → 4 → 5 → 6` | ① `_update_after_schedule` 里 `+= num_scheduled_token`<br>② `update_from_output` 里因投机 token 被拒而 `-= num_rejected`<br>③ `_preempt_request` 里被抢占时**清零** |
| `request.num_output_placeholders` | 请求状态 | **异步调度的"预支槽位数"**。CPU 排下一步时 GPU 上一步结果还没回来，于是先"假装"该请求会多出 $1+\text{spec}$ 个输出位置。<br>**非异步模式下恒为 0** | 非异步：`0` | 仅 `AsyncScheduler._update_after_schedule` 里 `+= 1 + cur_num_spec_tokens`，在结果回来时 `-= len(new_token_ids)` |
| `num_new_tokens` | **局部变量**（不是 request 字段） | **本步这个请求要 forward 的 token 数**<br>= `num_tokens_with_spec + placeholders - num_computed_tokens`，再被阈值/预算/上下文长度三次截断 | prefill `4`，之后 `1` | `schedule()` 内每轮循环重新计算 |
| `token_budget` | **局部变量**（不是 request 字段） | **本步全局 token 预算**，初值 = `max_num_scheduled_tokens`（默认 = `max_num_batched_tokens`）。每调度一个请求就扣除其 `num_new_tokens`，**扣到 0 本步结束**。是装箱问题里的"箱子容量" | 例如 8192 | `schedule()` 开头初始化；`token_budget -= num_new_tokens`；抢占时回收 `+=` |
| `self.max_model_len` | Scheduler 状态 | **模型最大上下文长度**（prompt + 生成的总上限）。用于 `num_new_tokens = min(..., max_model_len - 1 - num_computed_tokens)` 防止输入位置越界 | 如 32768 | `vllm_config.model_config.max_model_len`，不变 |
| `self.scheduler_config.long_prefill_token_threshold` | 配置项 | **"长 prompt"判定阈值**。prompt 长于该值即视为 long prefill，单步最多只算这么多 token，避免一个超长 prefill 独占整步预算、饿死其他请求。<br>`0` 表示禁用（不截断）；启用时默认取 `max_model_len * 0.04` | 例如 1310 | `config/scheduler.py`，启动时确定 |

## 关键点：`request.` 前缀的才持久，另两个是本步临时量

```python
num_new_tokens = (
    request.num_tokens_with_spec        # 请求状态：已知全部 token
    + request.num_output_placeholders   # 请求状态：异步预支槽位
    - request.num_computed_tokens       # 请求状态：已算进度
)
# ↓ 三次截断，都是"本步资源约束"
if 0 < self.scheduler_config.long_prefill_token_threshold < num_new_tokens:
    num_new_tokens = ...                       # ① 长 prefill 单步上限（配置）
num_new_tokens = min(num_new_tokens, token_budget)      # ② 全局预算（局部变量）
num_new_tokens = min(num_new_tokens,
    self.max_model_len - 1 - request.num_computed_tokens)  # ③ 上下文上限（Scheduler）
```

## 不等式里的用法

```python
request.num_computed_tokens + 2 - request.num_output_placeholders
    >= request.num_prompt_tokens + request.max_tokens
```

| 片段 | 含义 |
|---|---|
| `num_computed_tokens - num_output_placeholders` | 去掉"在飞槽位"后的**真实已确认进度** |
| `+ 1` | 上一步必然产生的那个真实 token（decode 稳态下 `computed` 领先 `tokens` 一个位置） |
| `num_prompt_tokens + max_tokens` | 序列的理论最大长度 $P + M$ |
| 整体 | 保守判断"即便草稿全被拒，也已到 `max_tokens` 边界"，则本步不再调度该请求 —— 保证 decode 批次整齐（uniform decode 优化） |

## 不变式小结（decode 稳态）

$$P \le \text{num\_computed\_tokens} = \text{num\_tokens} - 1 < P + M$$

- `num_prompt_tokens` 是**固定起点** $P$
- `num_tokens_with_spec` 是**移动的终点**（随输出增长）
- `num_computed_tokens` 是**追赶终点的进度条**
- `num_output_placeholders` 是异步下对进度条的**临时偏移修正**
- `token_budget` / `num_new_tokens` / `max_model_len` / `long_prefill_token_threshold` 是**约束**，决定进度条每步最多前进多少
