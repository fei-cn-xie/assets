P1 · 封面 | PP 流水线并行

大家好。今天只讲一件事:流水线并行,简称 PP。

为什么讲它?因为做大模型推理,最先卡住的往往不是算力,而是显存。
一张卡放不下,后面的优化都无从谈起。

今天只讲 vLLM main 分支的 GPU 路径,也就是 CUDA 和 NCCL 这一套。

我们按三件事走:PP 为什么存在、在 vLLM 里怎么跑、部署时怎么选。

先看整体结构。


P2 · 内容结构 | 四个板块:从背景到部署

全篇四个板块。

背景:参数量涨得比显存快,为什么 DP 和 TP 都不够用。
机制:切完之后为什么会有气泡,又怎么填。
实现:四种并行的分工、命令到 Worker、切层、传数据、采样回传。
部署:三条命令、七个硬限制、怎么排错。

三个问题贯穿全篇:该不该上 PP、vLLM 里怎么跑、出问题怎么查。

从第一个问题开始。


P3 · 背景 | 问题不是「算得慢」,而是「根本装不下」

2018 年 GPT-1 一亿多参数,一张卡随便放;2020 年 GPT-3 一千七百五十亿,
fp16 就要 350GB。

算笔账:fp16 每个参数两字节,80GB 的卡连 400 亿参数的权重都装不下。
70B 模型光权重就是 140GB。

这还没算 KV Cache,70B 每个 token 大约 320KB。

出路三条:改模型、换内存、切到多卡。只有第三条能随卡数扩展。

注意,DP 是复制模型,它解决吞吐,不解决装不下。

那模型能不能拆?能,因为它是层叠的。


P4 · 背景 | 模型是层层堆叠,层与层之间只流动 hidden states 与 residual

从 Embedding 到 LM Head,是一串首尾相接的层。
层与层之间只流动 hidden states 和 residual。

所以可以这样切:GPU0 放前 20 层,GPU1 放后 20 层,每张卡只装一段。

2018 到 2019 年有三个里程碑,都出自训练时代,今天只看推理沿用下来的部分:
GPipe 提出 micro-batch 流水线和气泡率;PipeDream 加了异步流水;
Megatron-LM 把 TP 和 PP 组合起来。

但 PP 的本质不是算得更快,而是把模型拆到更多卡上。
代价是计算变成串行,同一时刻只有一段在算。

先补一个基础概念:一次 forward 到底在处理什么。


P5 · 机制 | batch 是什么:从一条 prompt 到一次 forward

先说清楚:一次 forward 处理的不是一条请求,而是一个批。

一句话先过 tokenizer 变成 token id,加上采样参数,变成请求进入队列。
调度器每步挑一批请求,决定每条算多少 token。
这些 token 拼成一条扁平数组,就是 batch。

它不是矩阵,是变长拼接。
请求 A 五个 token、B 三个、C 四个,一共十二个,没有 padding。

为了让 kernel 知道每段从哪开始,用 query_start_loc 记前缀和:0、5、8、12。

长度每个 step 都在变:prefill 一次贡献很多 token,decode 每次只贡献一个。

为什么要再切成 micro-batch?为了让通信和计算错开:切成两段,一段在算的时候,
另一段在传。vLLM 里由 DBO 来做,按 token 区间切,切成两个 ubatch。

有了这个,再看流水线。


P6 · 机制 | 一张卡在算,三张卡在等:这就是「流水线气泡」

一个批进来,要顺序流过所有阶段:Stage0 算完给 Stage1,Stage1 算完给 Stage2。
同一时刻,它只能待在一个阶段上。

如果这时只有这一个批在飞,另外三张卡就没活干,利用率只有四分之一。

那多挂几个批呢?右上四根柱:一个批空 75%,两个批 60%,四个批 43%,八个批 27%。
规律是:同时在飞的批少于阶段数,就一定有卡在等;到了阶段数以上,稳态基本就满了。

公式是 (p−1)/(n+p−1):p 是阶段数,n 是同时在飞的批数。

所以气泡不是实现问题,是串行结构决定的;唯一的解法是让更多批同时在飞 ——
下一页看 vLLM 怎么做到。


P7 · 机制 | 让多个「批」同时在飞:每个阶段每时每刻都有活干

vLLM 没有去切批,而是把「队列里始终挂着 pp_size 个批」做进了调度器。

EngineCore 里有个 batch queue,深度等于 pp_size。
先把队列填满,没满就继续调度,满了才回收最老的结果。

源码里写得很直白:max_concurrent_batches 等于 pp_size;结果只从末段的 TP0 回收。

为什么恰好是 pp_size?因为每个阶段同一时刻只能算一个批,要 p 个批才能让 p 个阶段
都有活;再多的批也不会更快,只会多占 KV。

代价是同时驻留的 KV Cache 变多,单请求延迟也变高,
因为它要顺序走过 pp_size 跳。

机制清楚了,进代码。


P8 · 实现 | 从 --pipeline-parallel-size 到每张卡上的一个 Worker

PP 在 vLLM 里不是模型代码里的 if,而是一条链路。

参数进 ParallelConfig 算出 world_size;
Executor 建进程、建 PP 组;
每张卡一个 Worker;
Worker 里的 ModelRunner 吃上一段发来的 intermediate_tensors。

右下角是 rank 布局:TP=2、PP=2、四张卡。
虚线连的是 PP 组,同一个 tp 位置、沿 pp 各取一个 rank。

相邻两个 stage 的 rank 相差 tp,所以 TP=8、PP=4、32 卡时,
stage0 是 0 到 7,天然落在一台八卡机上。

PP 不是唯一的并行方式。先看清它和 DP、TP、EP 的分工,再看它们叠在一起怎么排卡。


P9 · 实现 | PP 切的是「层与层之间」,不是「层里面」

这张表是这一页的重点。

DP 切请求,几乎不通信,但不省显存。
TP 切一层里的矩阵,每层两次 all-reduce,带宽要求极高。
PP 切层与层之间,每个边界只传一次点对点。
EP 切专家,每层 all-to-all。

右边两张图:TP 是竖切,每层都要同步;PP 是横切,只在边界传一次。

量级上,8K token 的批、70B 模型,TP=8 大约 21GB,PP=2 只有 0.27GB。

所以第一条经验:节点内用 TP,跨节点用 PP。

这里说的 NVLink,是卡与卡之间的专用互联,H100 上单卡约 900GB/s,
是 PCIe 5.0 的好几倍,但它只在一台机器内。这也解释了 TP 为什么不跨机。

作为对照,华为昇腾用的是 HCCS,910B 大约 400GB/s,差不多是 H100 NVLink 的一半;
跨机走 RoCE,集合通信库是 HCCL。道理是一样的:机内高速、跨机普通网络。

分工清楚了,再看三种并行同时上时,卡具体怎么排。


P10 · 实现 | 三种并行同时上:每张卡同时属于 DP、PP、TP 三个组

举个例子:DP=2、PP=4、TP=2,一共 16 卡,两台八卡机。

左边一栏是副本 0,右边是副本 1;
每栏四行是四个 PP 阶段;格子里两张卡是 TP。

看图的顺序:先看两栏,再看行,最后看格内。

rank 的算法是先 dp 乘 PP 加 pp,再乘 TP 加 tp。G11 算出来是 11。

三个组的分工:DP 不传张量,只做步级同步;PP 每个边界一次点对点;
TP 每层两次 all-reduce,必须 NVLink。

扩容:装不下就先 PP 再 TP;不够快就加 DP 副本。

卡位定了,层具体怎么切?


P11 · 实现 | 均分 + 余数往前补 + 末段少一层

32 层、PP=3,vLLM 切成 11、11、10。

先均分,每段 10 层;剩 2 层,从倒数第二段往前补,末段不补。
因为末段还要放 RMSNorm 和 LM Head。

不在本段的层用 PPMissingLayer 占位,不分配权重、不参与计算,加载时也会跳过。

想手工平衡,设 VLLM_PP_LAYER_PARTITION,个数等于 pp,总和等于总层数。

层切开了,段与段之间怎么接上?


P12 · 实现 | 只传两个张量,而且发送之后不等

每个 stage 算完,把 hidden_states 和 residual 交给下一段。

两步:先发元数据,走 CPU 的 gloo,说明形状和 dtype;
再发张量本体,走 NCCL 点对点。

关键是发完不等:isend 立刻返回 handle,下一轮开头才 wait,通信被计算盖住。

还有个优化:TP 大于 1 时,每个 rank 只发自己 1/tp 的切片,
接收方在 TP 组内 all-gather 还原。

hidden 传过去了,但采样在末段,结果怎么回来?


P13 · 实现 | 只有末段能采样,但每一段都要知道新 token

只有末段有 LM Head,只有它能采样。
但每段都要知道新 token:首段拼输入,每段更新自己的 KV 和状态。

默认做法:末段采样后,在 PP 组内广播 prev_sampled_token_ids;
其余段在下一步 execute_model 开头收,直接写进 input batch,不经过 CPU。

另一条是调度器回填,只在没开异步调度时用。

一句话:所有 stage 维护同一份请求账本,只是各管各的 KV。

把三条线索合起来,就是一次 forward。


P14 · 实现 | 所有 stage 跑同一份代码,靠 is_first / is_last 分叉

worker 的 execute_model,每步四件事。

第一,等上一轮的发送落账。
第二,非首段异步收。
第三,跑本段的层。
第四,非末段异步发给下一段。

所以同一份代码在四种角色下执行:
首段不收只发,中间段收也发,末段收不发、直接采样。

读 vLLM 的 PP,读这一个函数就够了。

跑通了,算算账。


P15 · 实现 | PP 省的是显存,不是算力

PP 省的是显存,不是算力。

权重只加载自己那段,大约四分之一;
KV 只为自己那几层分配,也大约四分之一;
激活是本段的加一份收发缓冲;
Embedding 和 LM Head 只在首末段。

三个数字:70B 的 fp16 权重 140GB;
每 token 的 KV 约 320KB,PP=4 后每卡约 80KB;
8K token 过一次边界只有 128MB。

收益是容量和规模;代价是延迟变高、并发少时填不满,
而且模型要支持 SupportsPP。

吞吐要靠 DP,不是靠 PP。

账算清了,怎么开起来?


P16 · 实战 | 三条命令覆盖 90% 的场景

三条命令。

单机八卡:TP=4、PP=2。

两台八卡机:每机 TP=8,跨机 PP=2,用 Ray。

手工指定层数:VLLM_PP_LAYER_PARTITION 四段各 20 层,
个数等于 pp,总和等于总层数。

官方选型四条:单卡放得下就不要并行;单机放得下用节点内 TP;
单机放不下用 TP 乘 PP;没有 NVLink 的卡优先 PP。

进阶还有 --enable-dbo,把批再切成两块,让通信和计算重叠。

能开起来,还有哪些坑?


P17 · 实战 | 7 个硬限制 + 3 步排错

七个硬限制。

模型必须实现 SupportsPP;

EAGLE3 和 PP 不兼容,这条多说两句:EAGLE3 的草稿模型要用目标模型中间层的 hidden states
当输入,可 PP 把这些层分到了别的卡上,段间又只传 hidden 和 residual —— 中间结果根本过不来。
所以这个组合直接不支持,V2 runner 会报错。

Elastic EP 和 PP 不兼容;--enable-return-routed-experts 没验证;
torch_shm 和 PP 互斥;pp_size 不能大于层数;
同一 DP 组必须同时 generate,否则死锁。

排错三步:一看日志,确认首末段;二看批,所有 stage 必须拿到同一份
SchedulerOutput;三看通信,用 NCCL_DEBUG 确认走的是 NVLink 还是 IB。

性能不升反降,先问三个问题:并发够不够、首末段显存紧不紧、跨机走没走 IB。

最后收个尾。


P18 · 收尾 | 切层、接力、填满:PP 就这三件事

切、传、填,PP 就这三件事。

切:均分,余数往前补,末段少一层。
传:只传 hidden 和 residual,发完不等。
填:队列挂 pp_size 个批,每段都有活干。

三个数字:pp_size;max_concurrent_batches 等于 pp_size;
气泡率 (p−1)/(m+p−1)。
