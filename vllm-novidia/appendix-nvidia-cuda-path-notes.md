## 平台识别

`current_platform` 是模块级懒加载单例。`vllm/platforms/__init__.py:262-285` 的 `__getattr__` 在首次访问时调用 `resolve_current_platform_cls_qualname()` (`:212-252`)，后者遍历 `builtin_platform_plugins` (`:203-209`) 加上 `PLATFORM_PLUGINS_GROUP` 插件 (`:213`)，把返回非 `None` 的插件收进 `activated_plugins`；内置与 out-of-tree(OOT) 插件各只允许激活一个，否则抛 `RuntimeError` (`:231-248`)，全无则退化为 `UnspecifiedPlatform` (`:250`)。

CUDA 探测函数是 `cuda_platform_plugin` (`vllm/platforms/__init__.py:60-108`)：导入 `pynvml`，`nvmlInit()` 后要求 `pynvml.nvmlDeviceGetCount() > 0` **且** 当前 vLLM 不是 CPU 构建 (`vllm_version_matches_substr("cpu")` 为假，`:74-77`)。NVML 导入/初始化抛出的异常若类名不带 `nvml` 会重新抛出 (`:88-92`)；否则回退检查 Jetson (`/etc/nv_tegra_release`、`/sys/class/tegra-firmware`，`:97-104`)。返回限定名 `vllm.platforms.cuda.CudaPlatform` (`:108`)。对比：ROCm 用 `amdsmi` (`:111-129`)，XPU 用 `torch.xpu.is_available()` (`:132-151`)，CPU 走版本字符串/darwin (`:163-200`)——即 CUDA 是唯一用 NVML 做 GPU 计数探测的平台。

关键类属性集中在 `CudaPlatformBase` (`vllm/platforms/cuda.py:158-168`)：`_enum = PlatformEnum.CUDA`、`device_name = "cuda"`、`device_type = "cuda"`、`dispatch_key = "CUDA"`、`ray_device_key = "GPU"`、`dist_backend = "nccl"`、`device_control_env_var = "CUDA_VISIBLE_DEVICES"`、`ray_noset_device_env_vars = ["RAY_EXPERIMENTAL_NOSET_CUDA_VISIBLE_DEVICES"]`。`Platform.is_cuda()` 就是 `self._enum == PlatformEnum.CUDA` (`vllm/platforms/interface.py:160-161`)，`is_cuda_alike()` 包含 ROCm (`:191-193`)。

模块导入期副作用：`vllm/platforms/cuda.py:49` 关闭 cuDNN SDPA（`torch.backends.cuda.enable_cudnn_sdp(False)`）；`:846-858` 用 `pynvml.nvmlInit()` 是否成功在 `NvmlCudaPlatform` / `NonNvmlCudaPlatform` 之间选择，并立即调用 `CudaPlatform.log_warnings()`（`:860`，NVML 版实现见 `:793-808`，提示设置 `CUDA_DEVICE_ORDER=PCI_BUS_ID`）。

设备计数不走 `torch.accelerator.device_count()` 而是 `_cuda_device_count_stateless(envs.CUDA_VISIBLE_DEVICES)` (`vllm/platforms/cuda.py:52-75`、`:489-491`)，因为 `torch.cuda._device_count_nvml()` 的结果受 `CUDA_VISIBLE_DEVICES` 影响的时机问题；该函数用 `lru_cache(maxsize=8)` 以 `CUDA_VISIBLE_DEVICES` 字符串为 key。注意 NVML 自身不受 `CUDA_VISIBLE_DEVICES` 影响，因此 `get_device_capability`/`get_device_name`/`get_device_total_memory`/`get_device_uuid` 都先做 `device_id_to_physical_device_id` 映射 (`:594-633`)。

torch 设备设置：`CudaPlatformBase.set_device` 调 `torch.cuda.set_device(device)` 并 `torch.zeros(1, device=device)` 强制执行 (`:182-191`)；`manual_seed_all` → `torch.cuda.manual_seed_all` (`:193-195`)，被 `vllm/utils/torch_utils.py:405-412` 的平台钩子调用；`get_current_memory_usage` 用 `empty_cache`+`reset_peak_memory_stats`+`max_memory_allocated` (`:239-245`)。

`CUDA_VISIBLE_DEVICES` 的三处设置时机：(1) MP 路径在子进程创建时，经 `set_device_control_env_var` (`vllm/v1/engine/utils.py:262-276`) 与 `get_device_indices` (`:279-299`) 按 `data_parallel_rank`×`world_size` 切片；(2) Ray/DP actor 在生命早期由 `EngineCoreActor._set_visible_devices` → `_set_cuda_visible_devices` (`vllm/v1/engine/core.py:2029-2046`、`:2058-2085`) 写入，注释解释了为何必须配合 `RAY_EXPERIMENTAL_NOSET_CUDA_VISIBLE_DEVICES` 绕开 Ray 的 sticky 语义；(3) Ray executor 给每个 worker 设置节点上 **全部** GPU (`vllm/v1/executor/ray_executor.py:309-320`，`ray_executor_v2.py:382-388`)。

`current_platform.is_cuda()` 分支在 v1 内的落点（`vllm/v1` 全量 14 处）：`v1/sample/ops/topk_topp_sampler.py:37`（是否启用 FlashInfer 采样）、`v1/worker/gpu_ubatch_wrapper.py:91`（DBO 的 SM 切分仅 CUDA/ROCm 可用）、`v1/worker/gpu_worker.py:219` 与 `:403`（allocator 调参与 CUDA graph 显存估算，见下）、`v1/executor/ray_utils.py:554`（Ray 前置校验 GPU 数）、`v1/attention/backends/triton_attn.py:501`（`supports_quant_query_input`）、`v1/attention/backends/fa_utils.py:18/216/252`、`v1/attention/ops/merge_attn_states.py:73`、`v1/attention/ops/flashmla.py:12/22`、`v1/attention/backends/mla/indexer.py:614`（DeepGEMM）、`v1/attention/backends/mla/prefill/flash_attn.py:88`。

## 执行器与 Worker

执行器类在 `Executor.get_class` (`vllm/v1/executor/abstract.py:47-92`) 由 `parallel_config.distributed_executor_backend` 决定：`"ray"` → `RayExecutorV2`（若 `envs.VLLM_USE_RAY_V2_EXECUTOR_BACKEND`）否则 `RayDistributedExecutor` (`:60-68`)；`"mp"` → `MultiprocExecutor` (`:69-72`)；`"uni"` → `UniProcExecutor` (`:73-76`)；`"external_launcher"` → `ExternalLauncherExecutor` (`:77-80`)；传类或限定名字符串则直接解析 (`:53-59`、`:81-87`)。

该字段的默认值在 `ParallelConfig.__post_init__` (`vllm/config/parallel.py:831-876`)，而这条默认规则本身带 CUDA 分支：`world_size_across_dp > 1` 时先默认 `"mp"`，但 `current_platform.is_cuda() and self.nnodes > 1` 强制 `"mp"` (`:841-842`)；`current_platform.is_cuda() and current_platform.device_count() < self.world_size` 直接 `raise ValueError` 提示改用 Ray 或正确设置 `--nnodes` (`:843-854`)；TPU+SPMD 走 `"uni"` (`:839-840`)；DP backend 为 ray 或探测到 Ray 时改 `"ray"` (`:855-871`)；`world_size == 1` 时 `"uni"` (`:875-876`)。

`UniProcExecutor`（单卡/单进程）在 `:46-74` 构造 `WorkerWrapperBase(rpc_rank=0)`、`init_worker`、`init_device`、`load_model`，local_rank 从 `device_config.device` 的 `cuda:N` 后缀解析 (`:68-74`)。`MultiprocExecutor` 断言 `world_size == tp*pp*pcp` (`vllm/v1/executor/multiproc_executor.py:116-122`)，调 `set_multiprocessing_worker_envs()` (`:124`)，后者在非 CPU 平台把 `OMP_NUM_THREADS` 降到 1 以避免多 GPU 进程下的 CPU 争用 (`:1009-1037`)。`Executor.get_class` 由 `LLMEngine`/`AsyncLLM` 调用 (`vllm/v1/engine/llm_engine.py:144`、`async_llm.py:219`)。

Worker 侧：`GPU Worker.__init__` (`vllm/v1/worker/gpu_worker.py:107-158`) 设置 `torch.set_float32_matmul_precision` (`:124-125`)、创建 `ElasticEPScalingExecutor` (`:127-129`)、`WeightTransferEngine` (`:135-142`)、通过 `profiler_config` 校验 (`:150-154`)。

`init_device` (`:239-334`) 是 NVIDIA 特化的核心：`device_config.device_type == "cuda"` 之外直接 `raise RuntimeError` (`:308-309`)。CUDA 分支内先 `os.environ.pop("NCCL_ASYNC_ERROR_HANDLING")`（Ray 设置该变量会破坏 graph building，`:242`）；当 backend 非 ray/external_launcher、DP backend 非 ray、`nnodes_within_dp == 1` 时，用 `dp_local_rank * (pp*tp) + local_rank` 重算 `local_rank`，并用 `torch.accelerator.device_count()` 做边界断言 (`:244-272`)；随后 `torch.device(f"cuda:{local_rank}")` + `torch.accelerator.set_device_index` (`:274-275`)、`check_if_supports_dtype` (`:277`)、**在取显存快照之前**初始化 NCCL，以便把 NCCL buffer 计入已用显存 (`:279-289`)、`set_random_seed` (`:295`)、`gc.collect()`+`torch.accelerator.empty_cache()` (`:298-299`)、`MemorySnapshot`/`request_memory` (`:302-303`)。`num_ubatches = 2 if enable_dbo else 1` 决定 workspace 管理器规模 (`:312-313`)，再按 `VLLM_USE_V2_MODEL_RUNNER` 选择 `v1/worker/gpu/model_runner.py` 或 `v1/worker/gpu_model_runner.py` (`:316-330`)。

`load_model` (`:338-345`) 包裹权重内存池、`set_current_vllm_config`，以及 `_scoped_allocator_max_split(max_split_size_mb=20)`——后者在 `:214-236` 明确 `if not current_platform.is_cuda(): yield; return`，然后通过 `torch._C._accelerator_setAllocatorSettings` 临时改写 `max_split_size_mb`，退出时恢复 `PYTORCH_CUDA_ALLOC_CONF` 里的原值或 `SIZE_MAX`。

`determine_available_memory` (`:354-506`) 决定 KV cache 显存：若 `kv_cache_memory_bytes` 已指定则仍跑一次 `profile_run()` 只为编译，然后直接返回该值并跳过 profiling (`:366-384`)；否则在 `memory_profiling` 上下文中执行 `profile_run()` (`:388-392`)，读 `torch.accelerator.memory_stats(...)["allocated_bytes.all.peak"]` (`:394-396`)，并且**仅当** `current_platform.is_cuda()` 且 `cudagraph_mode != NONE` 时才调用 `model_runner.profile_cudagraph_memory()`（注释说明 ROCm/HIP/XPU 的 graph pool 与 `mem_get_info` 行为不同会产生错误估计，`:398-407`）。最终 `available_kv_cache_memory_bytes = requested_memory - non_kv_cache_memory - cudagraph_memory_estimate_applied` (`:443-447`)，其中 cudagraph 估计受 `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS` 控制（默认 True，`vllm/envs.py:1768-1772`），并在 `:467-504` 给出等价的 `--gpu-memory-utilization` 建议。

`compile_or_warm_up_model` (`:574-727`) 先按 `compile_sizes` 减去 cudagraph capture sizes 做 warmup (`:577-603`)，再 `kernel_warmup(self)` (`:608`，实现见 `vllm/model_executor/warmup/kernel_warmup.py:27-109`：DeepGEMM warmup `:29-37`、FlashInfer autotune 仅 Hopper `has_device_capability(90)` `:39-46`、FlashInfer attention 混合 batch warmup `:48-78`），然后 `capture_model()` (`:610-612`)，并把实测 graph pool 显存与估算值对比 (`:614-628`)；末 rank 上再跑 `_dummy_run`/`_dummy_sampler_run` 预分配 logits buffer (`:690-710`)，最后重置种子并启用 triton JIT 监控 (`:712-722`)。`profile_cudagraph_memory` 在 V2 runner 里是返回 0 的占位 (`vllm/v1/worker/gpu/model_runner.py:598-600`)。

`sleep`/`wake_up` (`:160-199`) 基于 `vllm.device_allocator.cumem.CuMemAllocator`（CUDA VMM API）；level 2 睡眠会把 `named_buffers()` 拷到 CPU 保存 (`:166-170`)，`wake_up` 时写回 (`:191-196`)，并在 `tags is None or "kv_cache" in tags` 时重建 block table 布局张量 (`:198-199`)。`_maybe_get_memory_pool_context` (`:201-212`) 同样依赖 `CuMemAllocator`。`initialize_from_config` (`:538-571`) 先写 `cache_config.num_gpu_blocks` (`:544`)、初始化 KV transfer group (`:551`)，再在 sleep 模式下用 `allocator.use_memory_pool(tag="kv_cache")` 包裹 `initialize_kv_cache` (`:553-560`)，随后初始化 routed-experts capturer (`:562-563`) 与 KV-zero 元数据 (`:565-571`，注释明确这些 GPU 张量要放在 CuMem pool 之外)。

`worker_base.py` 本身与设备无关：`WorkerBase.__init__` 只注入 `current_platform` (`vllm/v1/worker/worker_base.py:76-78`)；`WorkerWrapperBase.init_worker` (`:221-305`) 按 `parallel_config.worker_cls` 解析类（即 `vllm.v1.worker.gpu_worker.Worker`，由平台在 `vllm/platforms/cuda.py:222-223` 写入），并支持 `worker_extension_cls` 动态继承 (`:253-279`)。`GPUModelRunner` 的 `main_stream`/`output_copy_stream` 分别是 `torch.cuda.current_stream` 与 `torch.cuda.Stream` (`vllm/v1/worker/gpu/model_runner.py:138`、`:331-334`)。

## 模型执行与 CUDA Graph

输入准备在 `GPUModelRunner.prepare_inputs` (`vllm/v1/worker/gpu/model_runner.py:735-885`)：decode-first 排序 (`:744-748`)，`idx_mapping` 经 `async_copy_to_gpu` 异步 H2D 拷贝 (`:752`，spec-decode 的 `cu_num_logits` 同理 `:782`)，`query_start_loc` 用 `async_copy_to_gpu(..., out=self.input_buffers.query_start_loc)` 写入预分配 buffer 并把尾部 padding 为 `num_tokens`（注释：FA3 等要求非递减，`:792-800`），随后 `prepare_prefill_inputs`/`prepare_pos_seq_lens`/`combine_sampled_and_draft_tokens`/`expand_idx_mapping` 全部是 GPU 或 triton kernel (`:804-850`)，`seq_lens_cpu_upper_bound` 留在 CPU (`:852-859`)。`prepare_attn` (`:887-903`) 走 `BlockTables.gather_block_tables` 与 `compute_slot_mappings`。`vllm/v1/worker/gpu/input_batch.py:12-32` 的 `InputBuffers` 在 `device` 上预分配 `input_ids/positions/query_start_loc/seq_lens/dcp_local_seq_lens`，`make_dummy` 会为 full CUDA graph 形状做 padding (`:107-126`)。`vllm/v1/worker/gpu/block_table.py:12-69` 持有 `device` 上的 block table、slot_mapping 以及 `data_ptr()` 组成的 uint64 指针张量 (`:66-69`)；`compute_slot_mappings` 是 triton kernel (`:137-162`、`:217-278`)；`init_block_table_layout_tensors` (`:72-90`) 由 `post_kv_cache_wake_up` 重建 (`model_runner.py:583-584`)。

`execute_model` (`model_runner.py:986-1179`)：先更新请求/KV 状态并 `apply_staged_writes` (`:995-1001`)，`get_uniform_token_count` 判定是否 uniform decode (`:1011`、`cudagraph_utils.py:70-83`)，接着 `dispatch_cg_and_sync_dp` (`:1020-1028`) —— 该函数在 DP>1 时用 `dist.all_reduce` 在 `get_dp_group().cpu_group` 上同步 `num_tokens`/`cg_mode`/`uniform_token_count` 三行，取最保守的 cg_mode 与最大 token 数，保证各 DP rank 走同一张图 (`vllm/v1/worker/gpu/dp_utils.py:16-117`)。随后按 mode 分派：`CUDAGraphMode.FULL` 时先 `kv_connector.pre_forward` 再 `cudagraph_manager.run_fullgraph(batch_desc)`（显式 replay，不传输入张量，因为已拷进静态 buffer，`:1122-1128`）；PIECEWISE/eager 则在 `set_forward_context(...)` 中直接 `self.model(**model_inputs)` (`:1129-1147`)。PP 非首 rank 的 `intermediate_tensors` 会 `copy_` 进按 max capture size 预分配的持久 buffer，以匹配 graph 捕获地址 (`:1104-1119`，buffer 在 `load_model:317-326` 创建)。

`ModelCudaGraphManager` (`vllm/v1/worker/gpu/cudagraph_utils.py:86-117`) 持有 `dict[BatchExecutionDescriptor, torch.cuda.CUDAGraph]` (`:107`) 与 `current_platform.get_global_graph_pool()`（仅在 cudagraph 开启时取，`:108`）；`_init_candidates` (`:119-182`) 按 `cudagraph_mode.decode_mode()`/`mixed_mode()`/`separate_routine()` 生成候选：FULL decode 图要求 `num_reqs = num_tokens // decode_query_len` 且 uniform token count 精确 (`:137-149`)，PIECEWISE 图把 `num_reqs` 置 `None` 表示无需请求 padding (`:151-166`)。`capture` (`:188-248`) 在 `graph_capture(device=...)` 上下文（`vllm/distributed/parallel_state.py:1293-1310`，内部新建 `torch.cuda.Stream` 并让 TP/PP group 也切入 graph capture 模式）中，按 PIECEWISE → FULL 顺序捕获：PIECEWISE 直接调用 forward_fn 让 `CUDAGraphWrapper` 自行处理 (`:228-229`)，FULL 则 `torch.cuda.CUDAGraph()` + `torch.cuda.graph(graph, self.pool)` (`:234-245`)。`dispatch` (`:250-263`) 与 `run_fullgraph` (`:265-278`) 负责 replay，后者在 replay 前 `get_offloader().sync_prev_onload()` 以避免 H2D 拷贝与静态 buffer 竞争。`vllm/v1/cudagraph_dispatcher.py` 是平台无关的键值集合层：维护 PIECEWISE/FULL 两套 `BatchDescriptor` 集合 (`:44-47`)、`_compute_bs_to_padded_graph_size` (`:71-108`)、`initialize_cudagraph_keys` (`:165-232`)、`dispatch` (`:234-323`)。piecewise vs full 的实际裁决在 `CompilationConfig.resolve_cudagraph_mode_and_sizes` (`vllm/config/compilation.py:1310-1440`)，依据各注意力后端 `get_cudagraph_support()` 的最小值 `min_cg_support` 与 `min_cg_attn_backend`，在 `NEVER`/不足 `UNIFORM_BATCH` 时降级为 `FULL_AND_PIECEWISE`、`FULL_DECODE_ONLY`、`PIECEWISE` 或 `NONE`。捕获入口 `GPUModelRunner.capture_model` (`model_runner.py:603-644`) 用 `torch.cuda.mem_get_info()` 前后差值度量 graph pool 大小。

微批/DBO：`vllm/v1/worker/ubatching.py` 完全建立在 CUDA 流与事件上——`UBatchContext.__init__` 接收 `comm_stream`/`compute_stream` (`:25-37`)，`update_stream` 调 `torch.cuda.set_stream` (`:77-80`)，`_signal_comm_done`/`_wait_compute_done` 用 `torch.Event.record`/`stream.wait_event` (`:82-92`)，`dbo_get_previous_event` 在 compute stream 上执行回调 (`:193-199`)，`make_ubatch_contexts` 创建 `torch.Event()` 与 `threading.Event` (`:202-241`)。SM 级资源切分在 `vllm/v1/worker/gpu_ubatch_wrapper.py:91-110`，其中 `:91-93` 显式断言仅 CUDA/ROCm 支持，`:94-99` 用 `torch.accelerator.current_device_index()` + `num_compute_units` 计算 `comm_sms`/`compute_sms`。

采样在 GPU 上：`vllm/v1/worker/gpu/sample/sampler.py:63-119` 全程操作 GPU 张量，logits 先拷成 FP32 (`:130-131`)，依次应用 logit bias / penalties / bad words / temperature / min_p / top-k-top-p (`:133-167`)，再用 `gumbel_sample` (`:188-195`)，输出 `sampled_token_ids` 等 GPU 张量 (`:109-118`)；`logprob.py`、`penalties.py`、`bad_words.py`、`prompt_logprob.py` 为对应 GPU kernel 实现。GPU 专属优化在 `vllm/v1/sample/ops/topk_topp_sampler.py:35-74`：仅当 `logprobs_mode` 不要求返回中间 logits 且 `current_platform.is_cuda()` 时启用 FlashInfer 采样，用 `FlashInferBackend.supports_compute_capability(capability)` 二次校验，不满足时按是否显式设置 `VLLM_USE_FLASHINFER_SAMPLER` 选择报错或静默回退；`.py:432-435` 是唯一显式版本检查（要求 `flashinfer >= 0.2.3`）。`ASYNC` 输出由 `AsyncOutput` 用 main/copy stream 完成 (`model_runner.py:1239-1245`)。

## Attention 后端选择

入口 `get_attn_backend` (`vllm/v1/attention/selector.py:52-102`) 组装 `AttentionSelectorConfig` 后调用 `@cache` 的 `_cached_get_attn_backend` (`:105-136`)，后者把决策完全委派给 `current_platform.get_attn_backend_cls(backend, attn_selector_config, num_heads)` (`:113-117`)，并在返回后按 `backend.get_required_kv_cache_layout()` 调 `set_kv_cache_layout` (`:124-134`)。

注意：**本版本没有 `VLLM_ATTENTION_BACKEND` 环境变量**（全仓 grep 无匹配）。用户指定走 `--attention-backend` → `AttentionConfig.backend` (`vllm/config/attention.py:20`)，字符串大小写归一 + `"auto"`→`None` 的解析在 `:105-117`，最终由 `selector.py:99` 从 `vllm_config.attention_config.backend` 读取。MLA prefill 后端另有 `mla_prefill_backend` (`config/attention.py:55-59`)。

CUDA 侧实现是 `CudaPlatformBase.get_attn_backend_cls` (`vllm/platforms/cuda.py:282-374`)：若用户显式指定后端，先用 `validate_configuration` 校验，非法则 `raise ValueError`，合法直接返回 (`:292-309`)；否则 `get_valid_backends` (`:247-280`) 按 `_get_backend_priorities` 的优先级逐个 `validate_configuration`，收集合法项与失败原因，取优先级最高者 (`:331-374`，命中 `--block-size` 限制时给 warning `:347-366`)。`validate_configuration` 抛 `ImportError` 被折算为 `"ImportError"` 原因 (`:273-274`)。

优先级表由 `_get_backend_priorities` (`vllm/platforms/cuda.py:78-143`) 给出，是"哪些后端属于 NVIDIA"的最直接证据。非 MLA：`device_capability.major == 10`（Blackwell）时为 `FLASHINFER > FLASH_ATTN > TRITON_ATTN > FLEX_ATTENTION > TURBOQUANT` (`:128-135`)，其余为 `FLASH_ATTN > FLASHINFER > ...` (`:136-143`)。MLA：`major == 10` 为 `FLASHINFER_MLA > CUTLASS_MLA > FLASH_ATTN_MLA > FLASHMLA > TRITON_MLA > {sparse}`，其中 sparse 顺序又按 KV cache dtype（量化 → FlashInfer 优先 `:91-96`）与 `num_heads <= 16`（`FLASHINFER_MLA_SPARSE` 优先，否则 `FLASHMLA_SPARSE`，`:100-109`）；`major != 10` 为 `FLASH_ATTN_MLA > FLASHMLA > FLASHINFER_MLA > TRITON_MLA > FLASHMLA_SPARSE` (`:119-126`)。ViT 侧另有 `get_supported_vit_attn_backends`/`get_vit_attn_backend` (`:376-430`)。

后端枚举与类路径集中在 `vllm/v1/attention/backends/registry.py:34-87`：CUDA 常用 `FLASH_ATTN`(`:44`)、`FLASH_ATTN_DIFFKV`(`:45`)、`TRITON_ATTN`(`:48`)、`FLASHINFER`(`:62`)、`FLASHINFER_MLA`(`:63`)、`FLASHINFER_MLA_SPARSE`(`:66`)、`TRITON_MLA`(`:70`)、`CUTLASS_MLA`(`:71`)、`FLASHMLA`(`:72`)、`FLASHMLA_SPARSE`(`:73`)、`FLASH_ATTN_MLA`(`:76`)、`FLEX_ATTENTION`(`:78`)、`TURBOQUANT`(`:84`)。同表内的 `ROCM_ATTN`/`ROCM_AITER_*`、`XPU_MLA_SPARSE`、`CPU_ATTN` 永不出现在 CUDA 优先级表中，即 CUDA 路径不会选中它们。用户/第三方可经 `register_backend` 覆盖 (`:200-252`，`get_class`/`get_path` 尊重 `_ATTN_OVERRIDES` `:89-118`)。

计算能力门槛（后端自述，CUDA 上是实际生效的过滤条件）：`FlashAttentionBackend.supports_compute_capability` 要求 `>= (8,0)` (`vllm/v1/attention/backends/flash_attn.py:204-206`)，且 sink 需 `>= (9,0)` (`:208-222`)；`FlashInferBackend` 要求 `>= (7,5) and <= (12,1)` (`flashinfer.py:406-410`)，sink 依赖 TRTLLM attention (`:412-426`)；`TritonAttentionBackend` 返回 `True` (`triton_attn.py:386-388`) 但 `supports_quant_query_input = current_platform.is_cuda()` (`:501`)；`FlashMLABackend` 要求 major ∈ {9,10} (`mla/flashmla.py:73-75`)；`CutlassMLABackend` 要求 major == 10 (`mla/cutlass_mla.py:64-66`)；`FlashInferMLABackend` major == 10 (`mla/flashinfer_mla.py:64-66`)；`FlashMLASparseBackend` major ∈ {9,10} (`mla/flashmla_sparse.py:131-133`)；`FlashInferMLASparseBackend` 见 `mla/flashinfer_mla_sparse.py:100`。

flash-attn 版本探测全部集中在 `vllm/v1/attention/backends/fa_utils.py`。CUDA 分支在导入期绑定 `vllm._custom_ops.reshape_and_cache_flash` 与 `vllm.vllm_flash_attn.{flash_attn_varlen_func,get_scheduler_metadata}` (`:18-23`)，与 XPU (`:25-31`)、ROCm（上游 `flash_attn`，缺失时给出 stub，`:32-53`）区分。`get_flash_attn_version` (`:56-180`) 先按设备能力选默认：SM90 且支持 FA3 → 3 (`:78-80`)，SM100 且支持 FA4 → 4 (`:81-83`)，否则 FA2 (`:84-86`)；再被 `attention_config.flash_attn_version` 覆盖 (`:88-96`)；随后是回退矩阵：Blackwell 上禁用 FA3 (`:99-104`)、ALiBi 不支持 FA3/FA4 (`:106-116`)、SM90 上 head_size>256 或带 sink 的 diff-KV 升到 FA4 (`:118-140`)、`VLLM_BATCH_INVARIANT` 禁用 FA4 (`:142-149`)、Blackwell FA4 的 TMEM 限制使 head_size>128（192 除外）回退 FA2 (`:151-168`)；最后 `is_fa_version_supported` 断言 (`:170-178`)。`is_fa_version_supported` (`:183-191`)、`flash_attn_supports_fp8`（FA3 + SM90，`:194-200`）、`flash_attn_supports_quant_query_input` (`:203-204`)、`flash_attn_supports_sinks` (`:207-210`)、`flash_attn_supports_mla`（CUDA + FA3 + SM90，`:213-231`）、`is_flash_attn_varlen_func_available`（CUDA/XPU 恒真，`:234-261`）共同构成可供性判断。

## 显存与 KV Cache

显存剖析：`MemorySnapshot.measure` (`vllm/utils/mem_utils.py:96-126`) 用 `torch.accelerator.memory_stats(device)["allocated_bytes.all.peak"]`、`current_platform.mem_get_info(device)`、`torch.accelerator.memory_reserved(device)`，并定义 `torch_memory`/`non_torch_memory`；其中 `:109-116` 是 UMA 特例——若 `is_integrated_gpu()`（GH200/DGX Spark/Jetson 等 CPU-GPU 共享物理内存），改用 `psutil.virtual_memory().available`，因为 `cudaMemGetInfo` 不统计可回收的 OS 页缓存。`DeviceMemoryProfiler` (`:48-67`) 与 `memory_profiling` (`:191-274`) 提供前后差值。`init_snapshot` 与 `requested_memory` 在 `vllm/v1/worker/gpu_worker.py:302-303` 取得，`request_memory` 由 `--gpu-memory-utilization` 与 `total_memory` 推导（`vllm/v1/worker/utils.py:403`，在 `gpu_worker.py:303` 调用）。

KV cache 大小推导：`determine_available_memory` 返回可用字节（见上节，`gpu_worker.py:354-506`）→ `get_kv_cache_configs` (`vllm/v1/core/kv_cache_utils.py:1942-2074`) 取所有 worker 的最小可用显存（`_auto_fit_max_model_len` `:1836-1898`，`available_memory` 为 list，`limiting_worker_mem` 在 `:1866`）→ 每个 worker 内由 `get_num_blocks` (`:932-949`) 做 `available_memory // page_size // num_layers` 并 clamp 到 `>= 0`，再经 `may_override_num_blocks` (`:895-902`) 应用 `num_gpu_blocks_override`；本轮分配由 `_report_kv_cache_config` (`:1706`) 记录，容量关系由 `_pool_bytes_per_block` (`:905-929`) 给出。`vllm/v1/worker/gpu/model_runner.py:339-384` 把 `max_model_len`（encoder-decoder 模型取 `max_source_positions`）换算成 `max_num_blocks_per_group`，DCP 下除以 `dcp_size` (`:357-362`)，并对 `block_size <= 128` 向上对齐到 `128 / block_size` 的倍数（注释：TRTLLM 等后端要求，#39324，`:363-367`）。

GPU 块分配：`attn_utils._allocate_kv_cache` (`vllm/v1/worker/gpu/attn_utils.py:129-143`) 对每个 `kv_cache_tensor` 直接在 `device` 上 `torch.zeros(size, dtype=torch.int8)`，同一 tensor 由 `shared_by` 的多个层共享；`_reshape_kv_cache` (`:146-241`) 按后端 `get_kv_cache_shape`/`get_kv_cache_stride_order` 做 view/permute，混合模型再走 `_update_hybrid_attention_layout` (`:244-268`)；`init_kv_cache` (`:271-284`) 完成绑定。`initialize_from_config` 把 `num_gpu_blocks` 写回 cache_config 并（sleep 模式下）在 CuMem pool 内部分配 (`gpu_worker.py:538-560`)。KV cache 布局本身（NHD/HND）由后端 `get_required_kv_cache_layout()` 决定 (`selector.py:124-134`)。

NCCL 初始化：`init_distributed_environment` (`vllm/distributed/parallel_state.py:1358-1409`) 的 `backend` 默认值就是 `"nccl"` (`:1363`)，由 `Worker.init_device` 传入 `current_platform.dist_backend`（即 `"nccl"`，`gpu_worker.py:288`）；DP/多节点时按 `data_parallel_rank * world_size + rank` 偏移 rank 并改用 `world_size_across_dp` (`:1378-1408`)。CUDA 平台还实现 stateless 进程组：`CudaPlatformBase.stateless_init_device_torch_dist_pg` (`vllm/platforms/cuda.py:458-487`) 断言 `is_nccl_available()`，构造 `ProcessGroupNCCL.Options`、`ProcessGroupNCCL` 并 `_register_backend(device=torch.device("cuda"), BackendType.NCCL)`。设备 communicator 由 `get_device_communicator_cls` 指向 `CudaCommunicator` (`:436-440`)，后者在 `world_size > 1` 时创建 `PyNcclCommunicator` (`vllm/distributed/device_communicators/cuda_communicator.py:73-78`)，并按 `unique_name` 含 `"tp"` 与否决定启用 custom allreduce / torch symm mem / FlashInfer allreduce (`:44-58`)，`all_reduce` 的回退链是 `nccl symm mem → quick reduce(ROCm) → FlashInfer AR → custom AR → symm mem → pynccl → torch.distributed` (`:174-231`)。EP/EPLB 的 all-to-all 后端同样绑定 NVIDIA 特有实现（`DeepEP`、`mori`、`nixl_ep`、`flashinfer_nvlink_two_sided/one_sided`，`:117-166`）。TP 通信组构造见 `parallel_state.py:1569-1589`。

请求 batch 在 TP rank 间切分：入口是模型层的 `ColumnParallelLinear`/`RowParallelLinear`。`ColumnParallelLinear` 按输出维切分——`self.tp_size = get_tensor_model_parallel_world_size()` (`vllm/model_executor/layers/linear.py:456`)、`self.output_size_per_partition = divide(output_size, self.tp_size)` (`:458`)，加载权重时 `start_idx = self.tp_rank * shard_size` 后 `narrow` (`:561-564`)，`gather_output and tp_size > 1` 时额外 all-gather (`:591`)；`RowParallelLinear` 按输入维切分——`self.input_size_per_partition = divide(input_size, self.tp_size)` (`:1449`)，`forward` 中 `output = tensor_model_parallel_all_reduce(output_parallel)` (`:1554-1563`)。也就是说同一批 token 在每个 TP rank 上都完整执行，只是在每个线性层内部按头部/隐藏维分摊，并在 Row 层后 all-reduce 归约；注意力层另按 KV head 复制（`QKVParallelLinear` 在 `:979`，KV head 复制逻辑在 `:1031-1048`）。**每个 rank 的请求集合本身不切分**——切分的是权重与 KV head，序列维在 DCP/CP 场景下才按 `cp_size` 分摊（`gpu/model_runner.py:357-362`、`block_table.py` 的 `cp_*` 参数）。

PP 阶段切层：`make_layers` (`vllm/model_executor/models/utils.py:620-652`) 调 `get_pp_indices(num_hidden_layers, get_pp_group().rank_in_group, get_pp_group().world_size)` 得到 `(start_layer, end_layer)`，然后用 `PPMissingLayer()` 填充 `[0, start_layer)` 与 `[end_layer, num_hidden_layers)` (`:645-649`)，从而让所有 rank 拥有同名同形的 module 列表而只实例化自己的层。`get_pp_indices` (`vllm/distributed/utils.py:95-129`) 支持 `VLLM_PP_LAYER_PARTITION` 手工指定（`:111-122`），否则均分、余数从倒数第 2 个 partition 往前分配以避开末尾的 norm 层（`:123-129`）。`Worker.execute_model` (`gpu_worker.py:782-871`) 用 `AsyncIntermediateTensors` (`:74-103`) 做非阻塞 PP send/recv，并支持 `enable_sp` 时按 residual 是否 scatter 决定 all-gather 张量集合 (`:799-826`)。

## 并行与通信

P/D 分离的 KV 传输在 NVIDIA 上是 NIXL + RDMA/NVLink：`_NIXL_SUPPORTED_DEVICE` (`vllm/distributed/kv_transfer/kv_connector/v1/nixl/utils.py:17-30`) 为 `"cuda": ("cuda", "cpu")`（TPU 仅 `("cpu",)`，XPU 为 `("cpu","xpu")`），OOT 平台通过 `current_platform.get_nixl_supported_devices()` 追加 (`:30`)。`NIXLConnectorWorker` 校验 `self.device_type`/`kv_buffer_device` 是否在表中 (`nixl/worker.py:309-311`)，再决定注册到 NIXL 的内存类型：优先 `current_platform.get_nixl_memory_type()`，否则按 device 类型取 `"VRAM"`/`"DRAM"` (`:341-354`)，随后 `get_reg_descs(...)/register_memory(...)` (`:960-962`)、`prep_xfer_dlist`/`make_prepped_xfer`/`transfer` (`:1234-1240`、`:2230-2240`) 完成实际搬运；握手兼容性哈希见 `nixl/metadata.py:74-125`。连接器注册表在 `kv_connector/factory.py:167`。KV connector 在 worker 侧的挂钩是 `GPUModelRunner.initialize_kv_cache` → `get_kv_connector` (`vllm/v1/worker/gpu/kv_connector.py:125-132`)，`ActiveKVConnector` 注册 KV cache、设置 host xfer buffer 操作为 `copy_kv_blocks` (`:48-58`)，并在 `execute_model` 的前后调用 `pre_forward`/`post_forward`（`gpu/model_runner.py:1127`、`:1146`、`:1164`）。

KV offload 到 CPU 明确走 CUDA 批量拷贝：`copy_kv_blocks` 在 `vllm/distributed/kv_transfer/kv_connector/utils.py:215-217` 按方向选择 `current_platform.insert_blocks_to_device` / `swap_out_blocks_to_host`，而 CUDA 实现就是 `dst_cache[:, dst_block_indices] = _src_cache.to(dst_cache.device)` / `.cpu()` (`vllm/platforms/cuda.py:514-536`)。native 的 `kv_offloading_size` 路径用 `vllm/v1/simple_kv_offload/cuda_mem_ops.py`：模块文档说明 CUDA 12.8+ 经 `cuGetProcAddress` 取 `cuMemcpyBatchAsync`（`:62`、`:96-114`），`DmaCopyBackend` 在后台线程调用它（`copy_backend.py:14-24`），worker 用 `pin_tensor` 固定 host 内存 (`simple_kv_offload/worker.py:12-14`)；`vllm/_custom_ops.py:2804-2819` 的 `swap_blocks_batch` 即此封装（同时兼容 ROCm 的 `hipMemcpyBatchAsync`）。分页 offload 路径在 `vllm/v1/kv_offload/cpu/gpu_worker.py`：`pin_mmap_region` 用 `cudaHostRegister` 固定整个 mmap (`:89-108`)，`SingleDirectionOffloadingHandler` 持有 `torch.cuda.Stream`/`torch.Event` 池与 `stream.wait_stream(torch.cuda.current_stream())`、`stream.wait_event(last_event)` 的顺序保证 (`:30-36`、`:299-335`)，实际拷贝调 `ops.swap_blocks_batch(..., is_src_access_order_any=...)` (`:326-334`)。

调度/启动阶段的其它 CUDA 条件分支：`gpu_worker.py:214-236`（allocator 调参仅在 CUDA 生效）、`:398-407`（CUDA graph 显存估算仅 CUDA）、`:460-506`（据此给出 `--gpu-memory-utilization` 建议）；`config/parallel.py:839-854`（CUDA 的 nnodes/device_count 约束）；`v1/executor/ray_utils.py:554-566`（Ray 集群 GPU 数前置告警）；`v1/worker/gpu_ubatch_wrapper.py:91-93`（DBO SM 切分仅 CUDA/ROCm）。
