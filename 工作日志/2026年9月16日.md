# 2026年9月16日 工作日志

## 主题

请求终止（abort）功能的需求落地与验证；过程中定位并修复了上行数据传输通道的一个缺陷。

## 工作过程

1. **任务起点**：需求是"用户在推理未结束时终止请求（主动 abort 或客户端断连），服务端应停止推理、停止输出、释放资源，且不影响其他请求"。
2. **梳理现状**：核对代码后确认，终止功能的控制面逻辑此前已经实现——边侧发出终止通知、云侧完成终止与资源释放，下行方向（云侧把结果回传边侧）也能正确处理已终止请求的迟到数据。
3. **发现缺口**：继续核对两侧通道的"收发配对"关系时发现上行方向（边侧把整段 prompt 发给云侧）存在缺陷：如果请求被终止的时机恰好落在"边侧已发出数据、云侧尚未处理对应通知"之间，云侧会**直接丢弃这条通知、不再接收数据**。
4. **评估影响**：边侧的数据此时已经发出且无法收回，于是上行通道的序号出现空洞，**该通道后续所有请求的数据被永久阻塞**，云侧推理进程卡死，只能重启恢复——属于服务级故障，必须修复。
5. **实施修复**：把"丢弃通知"改为"按原长度接收后丢弃"，让通道序号继续推进、后续请求正常通行。不能简单"跳过"该序号：数据已发出无法收回，跳过会导致收发错位。

## 复现过程

这一步占用时间较多，记录如下：

1. **最初两次实测都没有复现**（终止后第二个请求仍能正常返回）。分析后确认原因是：云侧空闲时会立即消费那条通知，而终止信号到达总要晚一步，缺陷的触发窗口被错过。
2. **定位触发条件**：必须让"终止生效"早于"云侧消费通知"。由于边侧目前不支持把长 prompt 切块，一个请求只占一次上行传输，触发窗口只有一个调度步，自然条件下极难命中。
3. **排除两个干扰项**：① 启动参数中单批 token 上限设置过小（128），导致长 prompt 请求根本不被受理——与缺陷无关；② 临时插桩的请求匹配条件写错（服务端会给请求 id 加前后缀），插桩实际未生效。
4. **确定复现方案**：在云侧控制面接收线程中，把目标请求的通知延迟 3 秒再入队，从而把触发窗口拉开——终止信号必然先被处理，缺陷可稳定复现。
