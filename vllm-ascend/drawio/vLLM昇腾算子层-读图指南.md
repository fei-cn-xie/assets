# vLLM 昇腾算子层 · 读图指南

配套文件：`vLLM昇腾算子层.drawio`（10 页）。
定位：整套材料的**最底层**——前面十一套讲「算什么、怎么调度」，这一套讲
**「每个算子最后由谁执行、为什么快、为什么会有那些限制」**。

---

## 1. 十页清单

| 页 | 讲什么 | 一句话结论 |
| --- | --- | --- |
| ① | 算子层总览 | 模型图上的每一步都要落到一个具体 kernel；「谁在算」这张映射决定性能上限与限制条件 |
| ② | 一个算子 ≠ 一次下发 | 融合省的是「中间结果落显存再读回来」与下发次数，不是算力 |
| ③ | 矩阵乘家族 | 三类：普通线性（NZ 权重）/ 量化线性 / MoE 分组矩阵乘；**没有按形状切的魔法** |
| ④ | 小算子家族 | 归一化/激活/位置编码：融合收益最高，且按「模型族 + 硬件代次」分叉 |
| ⑤ | 采样的取舍 | 两处**故意不用**硬件算子：top-k/top-p（形状不规整时慢 5~28 ms）、多项式采样（会同步） |
| ⑥ | 通信算子 | TP 是「gather → GEMM → reduce-scatter」；真 all_reduce 只剩三处 |
| ⑦ | 六层闸门 | 融合算子要过六道闸门，任一不过就降档——「同代码不同机器差很多」的真正原因 |
| ⑧ | 算子总表 | 四组速查表：矩阵乘 / 小算子 / attention 与 KV / 路由与通信 |
| ⑨ | attention 落点 | prefill 与 decode 是「形状能力不同」而非新旧；**paged 是可选加速项，本仓没开** |
| ⑩ | 流与同步 | 一条主流 + 十几条旁路流；四个真同步点就是延迟热点；workspace 从 KV 预算扣 |

三条路径：

- **只想懂性能**：② → ③ → ⑦
- **要排障「为什么慢」**：⑦ → ⑩ → ③
- **要读 attention 代码**：⑨ → ④ → ⑧

---

## 2. 一页纸答案

**核心心智模型**：一个「数学上的一步」到硬件上可能是 **1 个融合 kernel**，也可能是 **3 个基础 kernel + 2 次中间结果落显存**。区别不在功能（功能一样），在**带宽与下发开销**。

**四条最值钱的结论**：

1. **融合算子的收益是「少读写 + 少下发」**，所以对 decode（带宽瓶颈 + 小 batch）最值钱；
   但融合算子对**形状/ dtype / 硬件**挑剔 → 本仓到处是「能融就融、不能融就分步」的回退。
2. **同一件事有三档实现**（图级再融合 / 厂商融合 / 分步基础），
   所以「为什么这台机器慢」= 「闸门关在哪一档」。
3. **TP 的通信不是 all_reduce**：本仓是「all_gather → GEMM → reduce-scatter」；
   真正的 all_reduce 只剩三处（输出头、共享专家、某个融合归一化 kernel 内）。
4. **paged attention 不是 decode 的默认算子**——它要在名单里才启用，本仓十套包都没配，
   所以本仓 decode 实际走的是融合 attention。**「decode 一定用 paged attention」是常见误解。**

**两个必须记住的数字**：
- 融合 attention 的变长布局：**每请求 query ≤ 16** → 决定投机解码 K 的天花板；
- chunked prefill workspace：与「token 上限 × 头维度」成正比，仓内注释给的例子是
  **288 MB 与 6 GB 只差在头配置**。

---

## 3. 四个容易搞错的点

1. **「小 batch 会自动用向量乘、大 batch 用矩阵乘」**——本仓**没有**这种形状分派；
   分派只看「权重怎么存」（量化与否）与并行配置。唯一接近「按形状选路」的是**融合通信**那条链。
2. **「硬件有融合算子就一定更快」**——错。采样路径有明确注释：硬件 top-k/top-p 在 k 大或混杂时
   **5~28 ms**，而排序+掩码稳定 ~1 ms，所以**主动不用**。
3. **「融合越多越好」**——不。有些地方是**为兼容故意不融合**（例如极小形状保持普通布局，
   因为分形布局的矩阵算子在 1×1 上会被直接拒绝）。
4. **「attention 的 prefill/decode 是同一套代码的两个分支」**——是两个不同算子，
   而且**能力也不同**（paged 只能表达单 token decode）。

## 4. 与其它十一套图的接口

- ① ← 站 1（Transformer 数学：每个算子算什么）+ 站 4 ⑯（权重怎么参与计算）。
- ②⑦ ← 站 6（图捕获）：两者都在削减「下发次数」，一个靠融合、一个靠录制。
- ③⑧ ← 站 0 ⑦（量化）：量化的每一种方案，最后都落到「用哪个算子」。
- ④ ← 站 1 ④⑫（RoPE / FFN）：位置编码与激活的模型差异，在算子层被放大成「四个落点」。
- ⑤ ← 站 3 ⑨（Step 循环）：采样在每一步的尾巴上，所以对延迟最敏感。
- ⑥⑩ ← 站 4 ⑤（ZMQ 三通道是**进程间**通信）、站 5（Mooncake 是**跨机**搬运）：
  本套讲的是**卡间**通信，三者层次不同，排障时别混。
- ⑨ ← 站 7 ⑦（投机解码的 K+1）：16 这个天花板就是从这里来的。
- ⑩ ← 站 6 ⑧（回放路径）：图重放前的那次同步就在这一页。

## 5. 怎么用它排「为什么慢」

```
① 先看启动日志有没有「自定义算子注册失败」的 warning        → 有就是二档
② 再看融合 pass 有没有「不启用」的原因（head_dim/形状/dtype）→ 有就是三档
③ 再看形状命不命中「名单」（例如 pa_shape_list 是否配了）    → 没配就少一条加速路径
④ 最后看同步点（图重放前 / 取计数回主机 / 分层 KV）         → 同步点通常是抖动来源
```

## 7. 图的来历与边界

三份并行只读走读（全部要求带 `文件:行号`）：

1. **attention 算子**：后端家族表（GQA/MLA/SFA/DSA/CP/310P）、prefill 与 decode 的算子差异与
   判定条件、布局族（变长拼接 / paged / 输入_输出组合）、每请求 16 token 天花板、workspace 算术、
   KV dtype 分支、以及本仓十套包的实测配置（**结论：都没开 paged attention**）。
2. **通用与通信算子**：linear/GEMM 三类的落点、归一化的三档融合、激活的变体、位置编码的四个落点、
   采样路径的两处反向选择、TP/EP 两套通信、MC2 的规模门槛、四类融合算子总表（40+ 条锚点）、
   六层回退机制。
3. **流与同步**：约 18 条流的用途、三处典型重叠、六个里程碑事件、workspace 管理器与显存账、
   图捕获对流的硬要求、九个关键同步点与它们的代价、下发开销的量化注释（每个 F.pad 两次 kernel ≈ 44 µs/层）。

**明确标为「未确认」的四处**：
① 生产环境实际启用了哪些融合算子（成功注册无 info 日志，只有失败 warning）；
② Python 层是否存在「小 batch GEMV / 大 batch GEMM」的形状分派（grep 未见）；
③ DSV4 包里 SWA/C4/C128 三种稀疏变体的**实际命中情况**（启动日志不打印后端类名）；
④ P 侧 profile 估算与运行时 workspace 用两套口径（是否影响显存预估未确认）。
