# vLLM 故障案例与排查 · 读图指南

配套文件：`vLLM故障案例与排查.drawio`（10 页）。
定位：前九套讲「它怎么工作」，这一套讲「**它坏的时候长什么样**」。
案例全部来自本仓根目录的**真实复盘文档**（20+ 份里挑了 8 个最有代表性的），
每个都按「现象 → 第一反应（错在哪）→ 排查路径 → 根因 → 修复 → 预防 → 教训」走一遍。

## 1. 十页清单

| 页 | 讲什么 | 一句话结论 |
| --- | --- | --- |
| ① | 排障方法论 | 四步法：分诊（崩/挂/慢/错）→ 定位层 → 对照实验二分 → 固化成断言 |

## 2. 八个案例的一句话根因

| # | 案例 | 根因（一句话） |
| --- | --- | --- |
| ② | ACL 图掉出 | 开了 MTP 后每请求占 4 个 token 位，但图的上限仍按「序列数」写 100 → 26 并发即掉出 |
| ③ | TTFT 47 s | 92% 是排队；D 段服务率只有物理上限的 38%（缺口来自 ②） |
| ④ | 指标全零 | 「有指标壳」只证明构造函数跑过；P 侧恒零是**正常态** |
| ⑤ | 级联故障 | 准入判据只查「单请求此刻够不够」，没有全局账本 → 分配失败 → 抢占断言 raise |
| ⑥ | 显存泄漏 | 覆写了带「不建计算图」装饰器的方法，图被请求级缓存钉住 |
| ⑦ | 槽位不归还 | 接管了 step，却没接管「按输出更新状态」里的归还逻辑 |
| ⑧ | 精度 63.8 | D 侧位置偏移算成 −1（应为 −640 量级），生成段位置与 KV 差 639 |
| ⑨ | 代码缺陷 | 分支移植丢了一行 `def`，调用点还在、定义没了 |

## 3. 十条误导线索（⑩ 页的表）

1. **decode 比 edge 晚死** → 跨机时钟没换算（实测差 75~110 s）
2. **服务卡住不动** → 引擎进程其实已经死了
3. **空转步数高 = 在忙** → 在等一个不会来的东西
4. **并发单调爬升 = 吞吐健康** → 背压没生效
5. **「上一轮 bug 已修」= 系统健康** → 死于另一个问题，且是修复把它暴露出来的
6. **OOM 报在某算子 = 那算子要得多** → 那是「只差最后一个大分配」的落点
7. **报错里的数字 = 预算/系数** → 可能是业务语义（模板里图像占位下标）
8. **客户端 500 = 客户端问题** → 前 N 条成功，服务端在第 N+1 条把自己打死
9. **指标全零 = 功能挂了** → 可能该角色本来就不产生
10. **分数能精确复现 = 归因正确** → 复现只校验评分口径，不校验因果链

## 4. 三条纪律（比技巧重要）

1. **先对齐时钟、再读日志**——跨机排障的第一步永远是校准，否则因果关系会整个反过来。
2. **报指标必须带上下文**：报延迟要同时给并发、长度分布、完成率；报吞吐要同时给是否掉出图。
3. **把结论落成断言**——本仓最值钱的建议就是那行启动自检日志：
   「graph covers up to N concurrent seqs (max_capture=…, query_len=…); max_num_seqs=… →
   above N runs eager」——有它，事故在拉起阶段就能发现。

## 5. 边界说明（重要）

本套**只引用**仓库内已有的复盘文档，不新增结论、不改任何脚本与代码。
其中：

- **有一处结论本仓文档自身标为「待定」**：spec_decode 指标全零的最终根因，
  文档给了三种可能（P 侧正常态 / 前端统计链在某分支不可靠 / 进程刚起），并明确
  「数据本身定不了」，需再跑三条命令定案。本套按原文如实标为「待定」。
- **有一处日志侧仍是未知项**：某次级联故障里两条批的静默丢失点，文档自述
  「待现场闭环的唯一未知项」。本套未编造。
- **代码缺陷类（⑨）按仓规只报告、不落补丁**：`assets/AGENTS.md` 明确禁止在部署仓放
  `*.patch` / `git apply` 步骤，历史上曾这么做并被撤销。

## 7. 图的来历

三份并行只读走读（全部要求「直接引用原文关键句 + 精确数值 + 文件:行号」）：

1. **性能类**：ACL 图掉出、TTFT/TPOT 劣化、spec 指标全零（三份文档共 883 行）；
2. **挂死与显存类**：边侧 decode 卡死、边侧 NPU OOM、精度 63.80、多模态挂死（四份 + 一份更正）；
3. **数据面与代码缺陷类**：LWD chunk mismatch（报告 + 调用栈全景）、部署仓真实发生的
   「放补丁被撤回」案例。

三份走读一致沉淀出的**通用手法**（⑩ 页的主体）：先立测量法、算物理上限、
找拐点而非斜率、把数字反推到业务语义、用不变量自检、把「缺什么日志」当反向证据、
把修复做成「互相兜底的两个不变量」。
